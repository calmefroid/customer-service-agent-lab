# 阶段 3：统一写操作确认协议

**基线**：`main@f9db6f1`

**公共契约**：`1.1.0`（仅做可选字段和联合类型的兼容扩展，不升级版本）

**范围**：00 定义共享协议和 API 边界；02 实现服务端状态、校验与写入；04 实现消费者确认卡

## 一、现状与兼容判断

- `ConfirmationRequest` 已包含请求 ID、服务端 operation、目标、草稿快照、风险、令牌、幂等键和过期时间。
- `ConfirmationDecision` 已表达 `confirm / modify / cancel`，但此前没有消费者到 Chat API 的正式命令格式。
- `ChatRequest` 的 `submit_*` action 和 `ChatUi` 的业务专用确认卡仍是实际提交路径；客户端可直接选择 action，无法证明它确认的是哪一份服务端草稿。
- `AgentEvent.ui` 已是消费者 UI 的公开通道，无需增加新的 AgentEvent 类型或调试字段。

本阶段在 1.1.0 内增加可选的 `ChatRequest.confirmation`、`ConfirmationCommand` 和 `ChatUi.kind = confirmation`，因此不提交公共契约升级申请。集成完成后，两个公开 Chat API 都拒绝旧 `submit_*` 写 action 并返回 `CONFIRMATION_REQUIRED`；旧分支只保留为编排器内部的固定 Evals 迁移夹具，不再是消费者可调用入口，也不得凭 action 直接执行公开写请求。

## 二、端到端协议

```text
业务准备草稿
  -> 02 创建并保存 ConfirmationRequest(pending)
  -> AgentEvent.ui { kind: confirmation, request }
  -> 04 展示服务端 operation、draftSnapshot、风险和 expiresAt
  -> ChatRequest.confirmation（不含 operation）
      -> 00 API 做线格式与字段白名单校验
      -> 02 按 confirmationRequestId 从 Store 取回 operation
      -> 校验 session / token / idempotency / expiry / state / snapshot
          -> cancel：终止，不写工具
          -> modify：终止旧请求，校验修改内容，创建新的 pending 请求
          -> confirm：Abort 复检 -> 原子抢占 executing -> 写工具 -> completed
```

### ConfirmationRequest（服务端到消费者）

必须包含：

- `confirmationRequestId`
- `operation`
- `confirmationToken`
- `idempotencyKey`
- `expiresAt`
- `draftSnapshot`
- `sessionId / traceId / target / risks / riskLevel / createdAt`

`operation` 只由服务端根据已授权业务路径生成。安全自动升级不是 `ConfirmationOperation`，直接进入 handoff。

### ConfirmationCommand（消费者到服务端）

- `confirmationRequestId`
- `confirmationToken`
- `idempotencyKey`
- `action: confirm | modify | cancel`
- `finalSnapshot`：`confirm` 和 `modify` 必填；`cancel` 禁止携带

命令故意不包含 `operation`、`draftSnapshot`、`expiresAt`、`sessionId` 或 `traceId`。API 拒绝未知字段，尤其拒绝客户端提交 `operation`。客户端显示的 operation 不能成为授权依据。

### 状态语义

| 动作 | 状态变化 | 是否写业务 Store | 响应 |
| --- | --- | --- | --- |
| `confirm` | `pending -> executing -> completed/failed` | 仅校验全部通过且未 Abort 后写入 | 业务成功 UI 或公开错误 |
| `modify` | `pending -> modified`，随后生成新的 `pending` 请求 | 否 | 新 `AgentEvent.ui confirmation`；旧令牌失效 |
| `cancel` | `pending -> cancelled` | 否 | 普通 final 消息；确认卡关闭 |
| 过期 | `pending -> expired` | 否 | `CONFIRMATION_EXPIRED`，要求重新准备 |
| 重放 | 返回同一幂等结果 | 不重复写入 | 与首次完成结果等价 |

```json
{
  "sessionId": "S-100",
  "message": "确认提交退换申请",

    "confirmationRequestId": "confirmation-100",
    "confirmationToken": "opaque-token",

```

修改请求把 `action` 改为 `modify` 并提交编辑后的 `finalSnapshot`；取消请求只提交三个不透明标识和 `action: cancel`。客户端提交 `operation` 或同时提交旧 `action` 时，API 返回 400。

确认成功继续使用当前 `AgentEvent.ui` 业务成功卡和 `AgentEvent.final`；失败使用现有 `AgentEvent.error`。消费者响应不得包含 Store 状态、内部 operation 映射、Trace payload 或 debug。

## 四、02 Business 任务接口

02 只修改其业务领域、Adapter 和业务 Store 所有权目录，并实现：

1. `ConfirmationStore`
   - 以 `confirmationRequestId` 为主键保存请求、令牌摘要、幂等键、状态、最终快照和结果引用。
   - 状态至少包含 `pending / modified / cancelled / expired / executing / completed / failed`。
   - 提供原子状态转换；重复 confirm 返回同一结果，不重复调用写 Adapter。
2. `prepare*`
   - 覆盖订单变更、物流催办、退换、维修工单、安装工单。
   - 服务端确定 operation 和草稿 schema，创建 Store 记录后返回同一 `ConfirmationRequest`。
3. `resolveConfirmation(context, command, signal)`
   - 按 requestId 读取 Store，再校验 session、目标、令牌、幂等键、过期时间和状态。
   - operation 必须来自 Store，不能来自 `ChatRequest.action`、消息文本或 `finalSnapshot`。
   - 对 finalSnapshot 做 operation 对应的字段白名单、必填项、不可变目标和业务状态复检。
4. 决策
   - modify 创建新的请求并旋转 requestId、token、idempotencyKey；旧请求不可继续确认。
   - cancel 只更新确认 Store，不调用写 Adapter。
   - confirm 在调用写 Adapter 前最后检查 `signal.aborted`，然后原子抢占 executing；Abort 发生在写工具开始前不得写业务 Store。
5. 安全和 Trace
   - 安全自动升级直接调用 handoff，不创建 ConfirmationRequest。
   - 写入 `confirmation`、`tool`、`error` TraceEvent，但不得记录原始 token、幂等键、手机号和地址。
6. 兼容桥
   - 阶段 4 切换完成前，旧 `submit_*` action 只能解析已有的服务端 pending 请求；没有 pending 记录必须拒绝，不能临时生成并立即确认。

02 交付测试至少覆盖伪造 operation、错 session、错 token、错幂等键、过期、修改后旧令牌失效、取消零写入、并发双击幂等、Abort-before-tool 零写入和安全升级绕过确认。

## 五、04 Consumer 任务接口

04 只修改消费者页面与组件目录，并实现：

1. 从 `AgentEvent.ui.kind = confirmation` 渲染通用确认卡；operation 只用于展示文案和选择已注册的字段组件。
2. 原样保存 requestId、token、idempotencyKey 和 expiresAt；不得自行创建或修改 operation。
3. confirm / modify 携带当前 `finalSnapshot`；cancel 不携带快照，也不得继续调用旧 `submit_*` action。
4. modify 必须等待服务端返回的新 ConfirmationRequest，再允许 confirm；不能在客户端把修改直接当作已确认。
5. 到期后禁用确认并引导重新准备；请求发送后立即禁用按钮，重试复用原幂等键。
6. 会话切换、卡片取消、成功或失败后清理不透明令牌；令牌不得写 URL、日志、反馈、localStorage 或消费者可复制文本。
7. 安全 handoff / safety 卡不显示普通确认按钮。

04 交付测试至少覆盖五类 operation 的展示、三种决策、编辑后新请求、过期、重复点击、会话切换和无 debug/Trace 泄漏。

## 六、00 装配与门禁

00 已完成：

- `ConfirmationCommand` 与通用 confirmation UI 契约。
- Chat API 的字段白名单、operation 注入拒绝和旧 action 冲突拒绝。
- 02 Confirmation Store 与五类服务端校验的串行集成。
- 04 通用确认卡的串行集成。
- 物流催办、破损退换、维修与安装工单的 prepare 路径统一下发 Store 签发的 `ui.kind=confirmation`。
- `ChatRequest.confirmation` 原样接入 `resolveConfirmation`；operation 只从服务端 Store 解析。
- modify 返回轮换三项不透明标识的新 ConfirmationRequest，cancel 返回普通终态，confirm 只在写工具成功后返回业务编号与现有成功 UI。
- `CONFIRMATION_EXPIRED` 等业务错误原码进入 `AgentEvent.error.code`；AbortSignal 从 Chat API 经 Runtime、注册编排器传到写工具前门禁。
- 公开 Chat API 禁止旧 `submit_*` 写 action；消费者响应没有新增 debug 或 Trace 字段。
- Evals 对通用确认 UI 按服务端 operation 做语义分型，继续保护三类既有场景而不把门禁放宽为任意确认卡。

实际集成顺序：02 Business `74c8a8a` -> `pnpm check` -> 04 Consumer `acc4956` -> `pnpm check` -> 00 Chat/Runtime 接线 -> 36 项固定 Evals 与端到端确认回归。

阶段 3 最终门禁：

- 当前全量 Vitest 与生产构建通过。
- 36/36 固定 Evals，指纹不回退。
- 五类写操作全部先收到正式 ConfirmationRequest。
- 伪造 operation、过期、取消、修改旧令牌、并发双击和 Abort-before-tool 均为零业务写入。
- 安全自动升级不进入确认 Store。
- 消费者 AgentEvent / ChatResponse 不新增调试字段。
