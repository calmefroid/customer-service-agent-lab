## 二、冻结的 Chat 与路由接口

### 1. 确定性 Chat action

| action | 触发时机 | 服务端行为 | 禁止行为 |
| --- | --- | --- | --- |
| `prepare_order_change` | 用户在 `purpose=order_change` 身份确认卡确认当前演示身份 | 读取可变更订单并调用 02 `prepareOrderChange`，只返回正式 confirmation UI | 不得调用 OMS 写 Adapter |
| `prepare_order_cancel` | 用户在 `purpose=order_cancel` 身份确认卡确认 | 读取可取消订单并调用 02 `prepareOrderCancel`，只返回正式 confirmation UI | 不得直接取消订单 |
| `confirm_return_identity` | 用户在 `purpose=return` 身份确认卡确认 | 调用 02 退换进度查询，返回 `return_status` | 不得返回其他用户申请 |

阶段 3 的 `ChatRequest.confirmation` 是唯一写提交入口。三个新 action 不代表用户已确认写入；前两个只能准备草稿，第三个是只读查询。

### 2. 四维规范路由

| 用户目标 / action | module | 兼容 intent | topic | action 输出 | confirmation |
| --- | --- | --- | --- | --- | --- |
| 修改地址自然语言 | `logistics` | `logistics_query` | `order.change` | `confirm_identity_then_prepare_order_change` | `true` |
| `prepare_order_change` | `logistics` | `logistics_query` | `order.change` | `prepare_order_change` | `true` |
| 取消订单自然语言 | `logistics` | `logistics_query` | `order.cancel` | `confirm_identity_then_prepare_order_cancel` | `true` |
| `prepare_order_cancel` | `logistics` | `logistics_query` | `order.cancel` | `prepare_order_cancel` | `true` |
| 退换进度自然语言 | `return` | `return_exchange` | `return.status` | `confirm_identity_then_query_return` | `false` |
| `confirm_return_identity` | `return` | `return_exchange` | `return.status` | `confirm_return_identity` | `false` |

当前 `Intent` 是兼容维度，不为订单 change/cancel 新增 Intent。topic 表达对象和子场景，action 表达下一步能力，module 保持现有消费者三模块模型。

### 3. 历史 Intent 归一化

01 在 `parseStructuredRoute` 校验前执行白名单归一化，不能接受任意字符串：

| 历史别名 | 规范 Intent | 条件 |
| --- | --- | --- |
| `troubleshoot` | `troubleshooting` | 无条件 |
| `create_return` | `return_exchange` | 无条件 |
| `create_service_ticket` | `service_ticket_create` | 无条件 |
| `query_service_ticket` | `service_ticket_query` | 无条件 |
| `order_query` | `logistics_query` | 无条件 |
| `service_ticket` | create 或 query | 仅可由 action/topic 明确判定，否则 schema_invalid |
| `repair_support` | troubleshooting 或 knowledge_query | 仅可由 topic/action 明确判定，否则 schema_invalid |

Trace 保存原始模型 JSON 的脱敏摘要，同时 RouteEvent.selected 只保存规范化结果。ChatResponse.intent 不得返回历史别名。

## 三、模块任务接口

### 01 Runtime

- 仅修改 Runtime/Models/Session 所有权目录。
- 为三类新目标补齐自然语言 fallback、Mock Text 路由和确定性 action 路由，严格输出上表四维值。
- 在模型结构化解析边界实现白名单历史 Intent 归一化；未知或歧义别名继续失败并进入现有安全 fallback。
- 安全、写确认优先级与 remainingIntents 不回退；取消订单是普通确认写操作，不得被误判为停止生成或 safety。
- 交付路由矩阵、别名、混合意图、无效输出和现有路由回归测试。

### 02 Business

- 复用现有 `prepareOrderChange(context, draft)`、`prepareOrderCancel(context, draft)` 和 `resolveConfirmation`，不再建立第二套确认逻辑。
- 提供 00 可调用的当前演示订单准备接口所需数据；不可变 orderId、订单状态和演示身份仍由服务端复检。
- 在 CRM 领域提供退换查询接口：按当前演示身份查询指定 requestNo 或最近一条申请，返回统一 `ToolResult`、来源元数据和公开时间线；空结果、超时、业务错误、系统错误均可注入。
- 退换记录补齐授权所需 customer/order 关联与状态事件；不得靠消费者提交 customerId 授权。
- `businessStore.reset()` 继续恢复 seed 订单/履约/物流/工单并清空订单变更、取消、催办、退换和新增工单；同时清空 Confirmation Store。
- 交付修改、取消、退换查询、错误注入、越权、幂等和 reset 测试。

### 03 Knowledge

- 保持 `resetKnowledgeStore()` 为 00 统一重置的唯一知识入口。
- 验证它同时恢复 seed 文章、发布快照、索引、草稿序号并清理 conflict/expired Sandbox 场景；如缺失，仅在 03 目录补齐。
- 不创建第二个 reset API，不修改 Chat、Business 或运营台。

### 04 Consumer

- `identity_confirm` 按 purpose 映射：order_change → `prepare_order_change`，order_cancel → `prepare_order_cancel`，return → `confirm_return_identity`。
- 订单草稿继续使用通用 confirmation 卡；客户端不得构造 operation、token 或幂等键。
- 渲染 `order_operation_success` 和 `return_status`；只显示契约公开字段，状态和时间线为空时有明确空态。
- 会话停止、失败重试和 debug 隔离不得回退。
- `feedbackStore.reset()` 由 00 统一 reset 协调器调用；消费者页不展示 Sandbox reset。

### 05 Operations

- `BusinessStoreQuery` 接入既有 `listOrderChanges()` 与 `listOrderCancellations()`。
- 添加 `order_change / order_cancel` OpsRecord 类型、字段转换、筛选、详情和 Trace session 链接；地址和手机号继续脱敏。
- 退换状态事件存在时展示时间线，不改变 Business Store。
- 运营台提供后台 Sandbox 重置按钮，调用 00 的 `POST /api/sandbox/reset`；必须有二次确认、处理中和成功/失败反馈。
- 05 不直接 import 各 Store 执行 reset，也不修改统一 reset API。

## 四、00 最终装配边界

功能分支返回后，00 串行审查并负责：

- `contracts.ts`、`mock-orchestrator.ts`、`orchestration/**` 与 Chat API 最终接线。
- prepare order change/cancel 必须返回 02 Store 原始签发的 ConfirmationRequest。
- 正式 confirm 成功将订单记录映射为 `order_operation_success`；modify/cancel 保持阶段 3 语义。
- 退换查询映射为 `return_status`，失败保留统一公开错误码。
- 创建后台 `POST /api/sandbox/reset` 与共享 coordinator。请求必须是 `{ "scope": "all", "confirmation": "RESET_SANDBOX" }`，否则 400；成功返回 `resetAt` 与已重置 scope，不返回 Store 内容。
- reset 顺序：阻止新 reset 并发 → Business/Confirmation → Knowledge/Scenario → Runtime Sessions → Trace → Feedback → Evals runs。任何参与者失败返回 503 与失败 scope；不得报告部分成功为完整成功。
- 统一回归后再允许合并到 main，不在功能分支之间互相合并。

## 五、测试门禁与保护项

- 每个功能提交合并后立即运行 `pnpm check`。
- 最终固定 Evals 必须保持 36/36，稳定指纹不得回退。
- 新增端到端：修改地址 prepare→modify/confirm、取消订单 prepare→confirm、退换查询身份/空结果/成功、统一 reset 前后数据、运营台新增记录。
- 未确认写入、重复确认、Abort-before-tool、安全自动升级、破损不判责、消费者 debug 隔离和 Trace 脱敏继续作为硬门禁。
- reset 后 seed 订单/履约/物流/工单/知识恢复，运行时新增记录、会话、Trace、反馈、Evals run 与知识异常场景清空。
